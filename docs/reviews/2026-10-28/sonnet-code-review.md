## 1. Summary

The extension works, and its security-critical background paths are noticeably more careful than the rest of the code. That covers sender allow-listing, local-only server start, the native host's origin/port/message validation, bounded parser requests and the parser client's offset validation. All automated checks I ran pass.

The weak points are:

1. **Untrusted text is written into `innerHTML` in many places** in the content script: subtitle/lyric text, third-party lyric metadata, LLM output and error strings. One of those sources (Kugou) is fetched over plain HTTP.
2. **A re-entrancy race in `checkAndInitVideo`** starts lyrics search and AI song-identification while the caption fetch is still pending. This was reproduced with the repo's own test harness.
3. **Several user-facing settings and README claims are not honoured** (Anki deck and URL, "enriched card to Anki").
4. **The shipped logic exists in two diverging copies**, and `run_tests.js` tests the stale copy.
5. **The manifest requests broad and partly unused permissions.** That makes the code's `permissions.contains` guards meaningless and leaves dead, unauthenticated proxy handlers in the worker.

## 2. Architecture overview

```
manifest.json (MV3)
├─ MAIN world, document_start : js/youtube-bridge.js
│     poll movie_player captions API; CustomEvents are the only link to the isolated world
├─ ISOLATED world, document_idle : lib/wanakana.min.js, js/japanese-parser.js,
│     lib/yomitan-deinflector.js, content.js (+ content.css)
│     content.js = GENERATED by build_content_js.py
│       ← data/kanji-dict.js (only SPECIAL_WORDS, KANJI_DB via regex)
│       ← lib/deinflect-rules.json (inlined)
│       ← ~3,400 lines of hand-written JS held in a Python string
├─ Service worker (type: module) : background.js
│     PARSE_JAPANESE → backend /api/parse        ENSURE_LOCAL_SERVER → native host
│     CALL_CUSTOM_AI → OpenAI-compatible URL      FETCH_LRCLIB_LYRICS (+Kugou over HTTP)
│     FETCH_YOUTUBE_CAPTIONS, FETCH_LYRICS_URL (no callers), OPEN_OPTIONS_PAGE
├─ popup.html/js, options.html/js (settings, tests of providers/Anki, TSV export)
└─ native/native_host.py + install_host.py : Linux native-messaging launcher for the
      external LangPlay Server.py (port-locked, origin allow-listed, flock'd)
```

Ownership boundaries, as built:

- **Reading and parsing** has three tiers. The Sudachi backend (via the worker and `LinguaPlayParser`) is preferred. Otherwise `tokenize()` falls back to `Intl.Segmenter` plus the in-bundle dictionary and Yomitan deinflector.
- **AI calls** are split. `opencode` goes through the worker. Gemini, DeepSeek, OpenRouter and the local Antigravity server are called straight from the content script on the YouTube origin (`content.js:1287-1442`). Credentials are read from `storage.local` into that script.
- **Lyrics** are fetched by the worker (LRCLIB, then Kugou), parsed in the content script and cached per video in `storage.local`.
- **Anki** is written directly by the content script to a hard-coded `127.0.0.1:8765`, plus a local `linguaplay_cards` list that Options/Popup export as TSV.

What is done well:

- Worker sender checks (`canRequestServerStart`, `background.js:13-20`) and local-only launch rules (`:22-57`).
- Native host: strict message schema, origin allow-list, exact-port match, `flock`, proxy-bypassing health check, no shell (`native/native_host.py`).
- Parser client: strict offset/surface validation, bounded LRU cache, in-flight dedup, generation reset on navigation and HTML-escaped romaji (`js/japanese-parser.js`).
- `formatSenseiMarkdown` escapes before formatting (`content.js:~3130-3185`).
- Version guards against late async results (`drawerContextVersion`, `subtitleRenderVersion`).

## 3. Verified defects (reproduced or proven from code)

### F1 — Untrusted text reaches `innerHTML` unescaped · P1 · confidence High (injection) / Medium (impact)

**Where**

| Sink | Untrusted source |
|---|---|
| `content.js:1978-1980` (`highlightedJp` → `lp-sentence-jp`, `lp-chat-context-sentence`) | Cue text from YouTube captions, LRCLIB/Kugou lyrics, user-loaded `.srt/.vtt/.lrc` |
| `content.js:1986-1992` via `generateSentenceRomaji` fallback (`:629-701`; non-kana characters pass through `resolveToHiragana`, `:433/453/459`) | same |
| `content.js:2719, 2724, 2761-2766, 2797` | `response.trackName`/`artistName` from LRCLIB/Kugou; `prefixBannerHtml` |
| `content.js:2848-2871` (`errBanner`, `identifiedBanner`) | LLM output derived from the video title; error strings from remote services |
| `content.js:2051-2088`, `:3373`, `:3394`, `:3403` (`renderPedagogicalBreakdown`, `${w.word}`, `${w.meaning}`, `title="${w.word} …"`, `${err.message}`) | LLM JSON (prompt-injectable from subtitle text); remote error messages |
| `content.js:3011-3014` (`backHtml` sent to AnkiConnect) and `options.js:337-338` / `popup.js:70` (TSV with `#html:true`) | subtitle `sentence`, stored `meaning` |

**Trigger and evidence**

- The cue parsers only strip complete tags (`replace(/<[^>]+>/g,'')`, `:816/:841/:871/:899`). A payload with no `>` survives, and the drawer code then supplies the closing `>` itself.
- I ran the real `handleTokenClick` in the repo's vm harness with sentence `<img src=x onerror=alert(1) 猫です` and clicked `猫`. The resulting `innerHTML` was `<img src=x onerror=alert(1) <span style="…">猫</span>です`. The HTML parser reads that as an `<img>` element whose attribute list ends at the `>` of the injected `<span …>`. The romaji fallback emits similar markup.
- I could not run that string in a live browser; the headless Chromium DOM check timed out and I abandoned it. YouTube's CSP very likely blocks inline `onerror` handlers, so script execution is **unverified and probably blocked**. Still reachable: markup injection, UI spoofing, external image loads (an attacker-chosen `src` is a tracking beacon), and unsanitised HTML written into the user's Anki collection, where card HTML renders in a richer webview.
- Kugou is fetched over `http://lyrics.kugou.com` (`background.js:234, 254`; `manifest.json:68`). On an untrusted network anyone can rewrite `trackName`/`artistName`, which reach `innerHTML` at `:2761-2766`.
- The parser path is safe: `japanese-parser.js:76` escapes and has a test. The Markdown chat path is safe. The gap is all the hand-written template literals around them.

**Fix:** add one `escapeHtml()` in the bundle (or build DOM with `textContent`/`createElement`). Apply it to every interpolated value in the sinks above. Escape `token.surface` and `activeText` before splitting and re-joining for highlighting. Escape `def`/`sentence` before building Anki `Back`. Prefer an HTTPS Kugou endpoint; if none exists, treat Kugou metadata as hostile.

**Test gap:** no test feeds markup through cues, lyric metadata, LLM JSON or Anki payloads. `test_japanese_parser.js:71` covers only the parser's romaji.

### F2 — `checkAndInitVideo` re-enters during the caption fetch · P2 · confidence High (reproduced)

- **Where:** `content.js:3590-3744` (generator `build_content_js.py:3415`); the trigger is `setInterval(checkAndInitVideo, 1000)` at `:3778`.
- **Mechanism:**
  - On a new video the function sets `currentVideoId = vid` (`:3611`) and then `await fetchYouTubeCaptions(vid)` (`:3676`). That function does up to four sequential network steps and has no timeout on steps 2-4 (`:1130-1283`; fetches at `:1186, 1200, 1247, 1259, 1272`).
  - The 1 s interval re-enters the function. `vid === currentVideoId`, so the first block is skipped.
  - The lyrics gate at `:3694` (`subtitleTimeline.length === 0 && lyricsFetchAttemptedVid !== currentVideoId && !isFetchingLyrics`) is true, so it runs `fetchLrclibLyrics` → `FETCH_LRCLIB_LYRICS`, and on a miss `identifySongWithSensei`.
- **Reproduction:** I copied the harness from `tests/test_review_regressions.js` into `/tmp/lpreview/race2.js`. It stubs `fetch` to stay pending, calls `checkAndInitVideo()`, then calls it again as the interval would. Result: `messages sent while caption fetch is still pending: [ 'FETCH_LRCLIB_LYRICS' ]`.
- **Impact:**
  - Videos that do have Japanese captions still trigger lyric lookups, and the title/channel go to LRCLIB, Kugou and, on a miss, the configured AI providers (see F7).
  - Whichever finishes last overwrites `subtitleTimeline` (`:3679` vs `:3708`), so lyrics can replace real captions or vice versa.
  - There is also a `lyricsFetchAttemptedVid`/`isFetchingLyrics` ordering hazard between the two flows.
- **Fix:** serialise `checkAndInitVideo` with an in-flight promise or a `videoInitInFlight` flag. Alternatively set a `captionsFetchPendingFor = vid` guard and have the lyrics gate respect it. Give every network step in `fetchYouTubeCaptions` an `AbortSignal.timeout`. Replace the unconditional 1 s interval with `yt-navigate-finish` plus a bounded retry.
- **Test gap:** the existing startup test (`test_review_regressions.js:209`) resolves `fetch` immediately and never overlaps two ticks.

### F3 — Anki settings and README claims not honoured · P2 · confidence High

- Options stores `linguaplay_anki_deck` and `linguaplay_ankiconnect_url` (`options.js:107-108`) and offers "Test AnkiConnect". `content.js` never reads either key (grep: zero hits). Quick Add posts to a hard-coded `http://127.0.0.1:8765` with `deckName: 'LinguaPlay'` (`:3020-3030`).
- A custom deck or URL therefore silently has no effect. The README's "Connect Anki" section says to set the deck and URL.
- "Save Enriched AI Card to Anki" (`:3467-3490`) only appends to `linguaplay_cards` and relabels itself "Saved to Storage". It never calls AnkiConnect. The README says that button saves "to Anki", and the label says Anki.
- Quick Add ends with `.catch(() => {})` (`:3038`) and always shows "✓ Saved to Anki Collection!" regardless of the AnkiConnect result. Both the local-list write and the card append are read-modify-write on `linguaplay_cards`, so rapid clicks can lose cards.
- **Fix:** read the two settings, report AnkiConnect success/failure (`result.error`), and share one `saveCard()` between the Quick Add and AI paths. Do the append in the worker to serialise it.
- **Test gap:** no test covers the Anki path at all.

### F4 — Manifest permissions are broader than the code needs; dead proxy handlers · P2 · confidence High

- `manifest.json:65-76` already grants `http://*/*` and `https://*/*`. `optional_host_permissions` (`:78-81`) then lists the same patterns, which does nothing.
- Consequences:
  - `chrome.permissions.contains` in the worker (`background.js:70, 119`) and the `permissions.request` flow in Options (`options.js:74-83`) can never deny anything. The "Allow access to this endpoint" safeguards are decorative.
  - The extension is effectively "read and change all data on all sites", which is a big Web Store and trust cost for a captions helper.
- **Unused permissions:** grep finds no use of `chrome.downloads` or `chrome.scripting`. `activeTab` is redundant with `tabs`/host permissions. Remove them.
- `FETCH_LYRICS_URL` (`background.js:421-445`) and `FETCH_YOUTUBE_CAPTIONS` (`:153-209`) have no callers anywhere in the repo. The lyrics-URL input UI was removed (`run_tests.js:806-807` asserts so).
  - `FETCH_LYRICS_URL` is an unauthenticated fetch-any-URL proxy (any `http(s)` URL including loopback/LAN, returns the body, no size cap, no `sender` check). A content-script compromise would turn it into a CORS-bypassing network probe.
  - `FETCH_YOUTUBE_CAPTIONS` duplicates `fetchInnertubeCaptions` in the content script.
  - Both are kept alive by tests (`test_lyrics_fetch.js:109, 169`; `run_tests.js:812-816`).
- `web_accessible_resources` (`manifest.json:82-`) exposes `options.html/js/css` and `icons/*` to every YouTube page. The only user is the `window.open` fallback (`content.js:2935, 2944`). This lets any page detect the extension and frame the options page; prefer `tabs.create` only.
- **Fix:** drop `http://*/*`/`https://*/*` from `host_permissions`. Keep the named API hosts and loopback, and request custom origins at runtime via `optional_host_permissions` as the code already intends. Delete the two dead handlers and their tests, and drop the unused permissions and the WAR entries for Options.

### F5 — The test suite validates a stale fork of the reading engine · P2 · confidence High

- `data/kanji-dict.js` exports its own `matchVerbInflectionAt`, `resolveToHiragana`, `segmentJapaneseSentence`, `generateSentenceRomaji` etc. (`:208-576`). `build_content_js.py:9-24` extracts only `SPECIAL_WORDS` and `KANJI_DB` from that file and then embeds a **second, hand-maintained copy** of these functions in the template, with the Yomitan deinflector added (`content.js:210-700`).
- `run_tests.js` (Suites 1-12) `eval`s `data/kanji-dict.js` (`:19-24`) and asserts on that copy. It never runs the shipped functions. The only suite that loads `content.js` is the Test 12e-12h block (`:684-718`), which makes four assertions.
- **Measured divergence** (`/tmp/lpreview/diffimpl.js`): I generated every dotted-kun entry × 20 inflection suffixes (75,940 words) and compared the two implementations. **452 differ**, e.g. `上げる` → shipped `あげる`, tested copy `うえげる`; `上がります` likewise. The shipped output is better here, which shows the "tested" code is not what runs.
- Additional drift risks:
  - `isJapaneseTrack` is copied verbatim into `js/youtube-bridge.js:10-24` and `content.js:1046-1060`.
  - The deinflection rules live in three places (`lib/deinflect-rules.json`, `lib/yomitan-deinflector.js:11`, and the bundle). `test_review_regressions.js:612` checks JSON ≡ deinflector, and my run confirms they are equal (37 reasons each). Both get loaded on every YouTube page (manifest content-scripts order), so the extension ships and executes the engine twice.
  - The generator uses a non-greedy regex (`r'export const SPECIAL_WORDS = ({.*?});'`) with no error path; if the file format changes it dies with `AttributeError: 'NoneType'…`.
  - Nothing asserts that `content.js` equals the generator's output. I verified it is byte-identical for this commit (`python3 -I build_content_js.py` produced no diff), but only because I ran it.
- **Fix:** make `data/kanji-dict.js` the single source of the functions (or move the functions into a real module the content script and tests both load), delete the fork, and add a CI check `python3 build_content_js.py && git diff --exit-code content.js`. Prefer plain `.js` source files and a bundler step over a 3.6k-line Python string with manual double escaping (see F8).

## 4. Design risks (mechanism verified, impact not exercised)

### F6 — Unbounded storage growth; write errors ignored · P2 · confidence Medium

- Per-video keys `lp_lyrics_cache_<id>` (full synced lyrics, `content.js:2772-2781, 3717-3726`) and `lp_offset_<id>` are never evicted. `cachedAt` is written but never read (grep: only the two writes). `linguaplay_cards` also grows without bound, and each Quick Add is a whole-array read-modify-write (F3).
- `manifest.json` does not request `unlimitedStorage`, so `storage.local` is subject to its ~10 MB quota. Every `storage.local.set` in the code is called without checking `chrome.runtime.lastError` (e.g. `options.js:96-113` shows the "Saved" toast unconditionally).
- Impact: after long use, saves of settings or API keys would fail silently along with cache writes. I did not reach the quota, so the threshold is arithmetic, not observed.
- **Fix:** LRU-cap the cache (use the `cachedAt` you already store), check `lastError` and surface it, and store the lyrics cache separately from settings or cap its total size.

### F7 — Privacy: automatic fan-out to multiple third parties · P2 · confidence Medium

- `identifySongWithSensei` (`content.js:1473-1580`) builds `candidateProviders` from the selected provider **plus every other provider that has a key configured**, then tries them in order (`:1512-1520`). Video title and channel are sent to each until one answers. The user chose one provider.
- It runs automatically when no captions/lyrics are found (`:3694-3728`), so the user need not click anything (and see F2 for the extra triggers).
- Every clicked word and sentence goes to Google's unofficial `translate.googleapis.com/translate_a/single?client=gtx` endpoint (`:1771, 1935`), with no opt-out and no mention in the README. `fetchSentenceTranslation`'s cache is an unbounded `Map` (`:1762`).
- Provider calls run in the content script, so API keys are loaded into the YouTube page's process, and the Gemini key is sent as a URL query parameter (`:1302`; also `options.js:128`), which tends to land in logs and error traces. Routing is inconsistent: `opencode` goes through the worker but the others do not (compare `:1394-1407` with `:1300-1392`), so the content script is subject to YouTube-origin CORS and mixed-content rules for those providers and for a non-loopback local server URL.
- **Fix:** restrict the song-ID fallback to the selected provider, document the translation endpoint (or make it a setting), and move all outbound provider calls into the worker so keys never enter the page process (also fixes the CORS inconsistency).

### F9 — Bridge polls forever and fights the user · P3 · confidence Medium

- `js/youtube-bridge.js:129` runs `ensureJapaneseTrackActive` every second on every YouTube page for the lifetime of the tab. When enabled, each tick calls `player.loadModule('captions')` (`:59-60`), reads the track list, and **switches the track back to Japanese and clicks CC if it is off** (`:37-44, 54-89`).
- With the app on, a user cannot select a different caption language or turn CC off for longer than ~1 s. The README flow ("hide the overlay with the eye control and turn on YouTube's CC") only works because switching off the logo is the escape hatch.
- `isJapaneseTrack` also treats any `vssId` containing "ja" as Japanese (`:15`), which is broader than intended.
- `test_youtube_bridge_toggle.js` covers only enable/disable, not the override behaviour.
- **Fix:** act on `yt-navigate-finish`/caption-change events and a bounded retry instead of an endless interval, and respect an explicit user track or CC choice.

## 5. Quality, maintainability, hygiene (P3)

- **F8 — Prompt-quote escaping is a no-op (generator bug).** `build_content_js.py:1327-1328` writes `'\\"'` in a normal Python string, which emits `'\"'` into JS (`content.js:1501-1502`). In JS that is just `"`, so `title.replace(/"/g, '\"')` does nothing and a title containing quotes breaks out of the quoted prompt field (prompt injection from video titles). Fix with a JSON-encoded value or `'\\\\"'`, and move to non-escaped source files (see F5).
- **F10 — `background.js` structure and duplication.**
  - `decodeKugouLrc` and `fetchKugouLyrics` are declared **inside** the single `onMessage` callback, between two `if` blocks (`:211-278`), with broken indentation; the file is one ~400-line callback.
  - The Innertube payload with hard-coded `clientVersion` and `signatureTimestamp: 20717` appears twice (`background.js:156-189`, `content.js:~1160-1198`).
  - `fetch` calls at `background.js:191` and `content.js:1186, 1200, 1247, 1259, 1272` have no timeout. `request` is dereferenced without a type check (`:60`).
  - Split handlers into named functions in a dispatch table.
- **F11 — Hard-coded caption probe.** `content.js:1218` calls `http://127.0.0.1:8000/api/captions` from the YouTube page on every video, ignoring `linguaplay_server_url`. Any local service on port 8000 can inject "subtitles", and newer Chrome versions may show local-network-access prompts for this (conjecture, not tested).
- **F12 — Two TSV exporters that disagree.** `popup.js:64-72` replaces only the first occurrence and omits `sentence_en`; `options.js:330-340` replaces all and includes it. Both hard-code `#deck:` and ignore the deck setting (see F1 for the HTML-escape gap in both). Extract one shared module.
- **F13 — Dead code, stale docs, repo weight.**
  - `drawerActiveWord` is write-only (`:745, 1922, 3621`).
  - Every branch of the `行` special case in `matchVerbInflectionAt` returns `'い'` (`:324-328`).
  - `typeof switchDrawerTab === 'function'` is always true.
  - Comments claim "<0.1 ms" for the deinflector; I measured 0.7-8 ms (cold) on typical inputs (`/tmp/lpreview`). The fallback romaji of a 43-character line cost ~3 ms warm, so there is no performance problem, just a wrong claim.
  - `PARSING_VERIFICATION.md` is labelled historical, but quotes 67 tests/13 suites versus the current 86 tests/15 suites.
  - `japanese-romaji-architecture.html` (820 KB, 15k lines, third-party generator output) is referenced by nothing and lives in the extension root. Move or drop it.
  - `lib/deinflect-rules.json` is a single-line file, so `wc -l` shows 0.

## 6. Test quality and gaps

State of the suites: all pass (details in §8). Overall they are behavioural where it counts (parser client, worker handlers, native host, harness-driven drawer tests) and the browser checks are broad and use a disposable profile. The weaknesses:

1. **Source-text assertions stand in for behaviour:** `run_tests.js:799-816` and `test_lyrics_fetch.js:268-280, 363, 437-448` check that `content.js` *contains* identifiers. These cannot fail for a behavioural regression.
2. **Tests encode the F4 problems:** `test_lyrics_fetch.js:109` asserts the broad host permissions, and `:169` tests the dead `FETCH_LYRICS_URL` handler.
3. **No coverage for:** HTML escaping of cue/lyric/LLM/Anki content (F1), concurrent `checkAndInitVideo` ticks (F2), the Anki paths (F3), storage errors/quota (F6), the bridge's CC/track override (F9), `install_host.py` output permissions, and generator freshness (F5).
4. **The real Sudachi integration is skipped by default** (`japaneseParsing: skipped` in the browser run). `PARSER_SERVER_DIR` is not set in CI-like usage, and the backend lives in another repo.
5. **Harness fidelity:** `createContentHarness` uses a hand-written `Element` whose `innerHTML` setter regex-strips tags (`test_review_regressions.js:44-52`). It cannot detect markup-injection bugs, which is exactly the F1 class.

## 9. Limitations

- Nothing was run against live YouTube, real provider APIs, a real Anki, or the Sudachi backend (it lives in another repository).
- F1's script-execution impact depends on YouTube's CSP and Trusted Types behaviour in the isolated world. I did not confirm it in a live page, and a headless DOM check I attempted timed out.
- F6's quota threshold and F11's Chrome local-network behaviour are reasoned, not measured.
- The 3.6k-line generator template was verified through the generated artifact rather than read line by line.
- Test files other than the ones named in §7 were skimmed, not audited assertion by assertion. Kanji dictionary content and the vendored wanakana build were not reviewed.
- Windows/macOS native-host paths are unsupported by design and were not considered.
